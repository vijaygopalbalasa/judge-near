# judge-wasm build notes

Deterministic ERC-8183 judge, ported from Judge Protocol's MIT JS engine to
Rust for wasm32-wasip1. Reads judge input JSON on stdin, writes the verdict JSON
on stdout, per ../docs/interface.md sections 1 to 3.

## Status (Nov 1 2026)

- Library + binary implemented. `cargo test` green: 24 tests.
  - 12 lib unit tests (text/type/url/email/hash helpers, whole-word vs reference
    on a 20k random sweep, overlapping-occurrence cases)
  - 7 edge tests (invalid_input, too_large, known hashes, err shape, key order,
    plain-vs-whole-word memo isolation)
  - 4 parity tests (full verdict string, structured fields, eh recompute, size)
  - 1 size sweep (1200 generated inputs, all <= 900 bytes, keys in order)
- Parity: 305 vectors in vectors/parity.json, generated by scripts/gen-parity.mjs
  from the JS engine run through the same pipeline with the interface overrides.
  The Rust output matches the oracle's verdict string byte-for-byte on all 305.
  parity.json is byte-identical before and after the whole-word linearization
  (that change altered cost, never a verdict).
- Longest verdict seen: 326 bytes (limit 900).

## Performance (see RESOURCE-LIMITS.md)

- Whole-word `contains` is linear: each deliverable is indexed once (code points
  + word flags), each term matched with KMP, repeated terms memoized, the
  deliverable parsed/word-counted at most once per evaluation (engine::Ctx).
- Worst case over adversarial-but-valid inputs (16 KB deliverable, 4 KB criteria,
  <=16 checks): 0.59 billion instructions (wasmtime fuel), 1.75 MB linear memory,
  ~21 ms, measured under OutLayer's metering. Earlier O(n*m) whole-word scan
  peaked at 17.4 billion, over the 1B default; the fix removed that stall vector.
- Recommended request_execution limits: 3B instructions, 16 MB, 5 s.

## Key parity decisions (verified against the JS oracle and empirically)

- serde_json with `arbitrary_precision`: `1e400` parses (as JS JSON.parse does,
  to Infinity); `as_f64()` is None for out-of-range, which is the "non-finite
  number" signal. Numbers compared by f64 value so 1 == 1.0 (JS `===`).
- `length` unit "chars" counts UTF-16 code units (JS `String#length`); json-shape
  minLength/maxLength count Unicode code points (`[...s].length`).
- Word count = maximal non-whitespace runs using the ECMAScript WhiteSpace set
  (includes U+FEFF, excludes U+0085); NOT Rust `char::is_whitespace`.
- `contains` wholeWords uses the code-point reference from the JS test suite.
- schema `typeof`: null and array are "object"; a number is always "number".
- Interface overrides over the JS engine: at most 16 checks (JS allowed 64);
  `http-endpoint` is not a known kind (any such check -> invalid_criteria);
  criteria <= 4096 bytes, deliverable <= 16384 bytes (else too_large).
- err priority: invalid_input -> too_large -> invalid_criteria. err verdicts use
  th:100 and checks:[]. ch/dh are sha256 of the exact decoded strings, or
  sha256("") for a field that could not be read.

## Deviations from a literal JS port (see interface; listed in final report)

- A deliverable nested deeper than serde_json's 127-level limit is "not valid
  JSON" to the Rust `json`/`schema` checkers and fails; V8 would parse it. The
  depth-100 parity vector confirms both agree below the limit; deeper inputs are
  excluded. (Criteria this deep are rejected earlier by the depth-12 gate in
  both, and DEEP_TEXT criteria hit the 4096-byte too_large gate first.)

## Fuel regression guard

An adversarial corpus and a guard keep the worst-case instruction count from
regressing past the recommended `max_instructions` (the stall vector of
interface.md section 4). All measured under wasmtime fuel, the metering OutLayer
uses, on judge.wasm `da3b581d84561c4cf1e4fe4a21e190f12b24f9c8bd0e96ad4c8e40e929f956f1`.

- `scripts/make-fuel-corpus.mjs` writes 15 adversarial inputs to `vectors/fuel/`
  (committed), each within the interface limits and on the scoring path: ~1,266
  empty wholeWords terms over spaced and solid 16 KB text (the pre-linearization
  17.4-billion case), ~783 distinct letters and 85 `a..ab` runs each found only at
  the end (defeating memoization), a 1024-unit late mismatch, 16x length /
  checksum / schema / json including nested `anyOf`, ~1,457-item `uniqueBy`,
  `uniqueBy` over URL domains, a max-size emoji+combining deliverable, and a
  normal scored case.
- `scripts/fuel-check.sh [cap] [wasm]` runs the judge over every corpus file under
  a fuel cap (default 3,000,000,000, the recommended `max_instructions`) and fails
  if any case runs out of fuel or does not print a verdict. Build the wasm first
  (BUILD.md), then run it. It needs only wasmtime and the committed corpus.

Results on `da3b581d`:
- fuel-check at 3,000,000,000: all 15 cases pass (per-run wall 6 to 38 ms, which
  includes wasmtime process start and JIT of the module; the guest run itself is a
  few ms). Negative control: at a 50,000,000 cap the guard correctly fails 5 cases.
- Precise worst case (binary-searched by `scripts/measure-limits.mjs`): 589,750,000
  instructions (16 json checks, nested `anyOf` over nested arrays), 1,792 KiB
  linear memory (16 json checks over ~1,457 items with `uniqueBy`), about 21 ms
  including about 5 ms compile and start. The whole-word families, once the
  17.4-billion ceiling, now top out near 577 million (the ~783 distinct-letter
  case).

Recommended `resource_limits` (full reasoning and deposit math in
RESOURCE-LIMITS.md): `max_instructions` 3,000,000,000 (about 5x the 0.59B worst
case, far under the 500B testnet cap), `max_memory_mb` 16 (about 9x the 1.75 MB
peak), `max_execution_seconds` 5 (the worker floors the timeout at 5 s, and this
is the field that scales the deposit, so no higher). `build_target` is
`wasm32-wasip1`.
