# judge-wasm build notes

Deterministic job-escrow judge, ported from Judge Protocol's MIT JS engine to
Rust for wasm32-wasip1. Reads judge input JSON on stdin (and, for sealed jobs, the
JN_KEY environment variable), writes the verdict JSON on stdout, per
../docs/interface.md sections 1 to 3 and 6.

## Status (Nov 2 2026)

- Library + binary implemented, public and sealed jobs. `cargo test` green: 38 tests.
  - 20 lib unit tests (text/type/url/email/hash helpers, whole-word vs reference
    on a 20k random sweep, overlapping occurrences, strict base64 with the RFC 4648
    vectors, HKDF without salt against RFC 5869 case 3, X25519 against RFC 7748,
    the k format, a small-order client key)
  - 7 edge tests (invalid_input, too_large, known hashes, err shape, key order,
    plain-vs-whole-word memo isolation)
  - 4 parity tests (full verdict string, structured fields, eh recompute, size)
  - 5 sealed tests (42 vectors byte for byte, the client round trip in Rust, a
    sealed verdict minus k equals public mode over the plaintext, the 897-byte
    longest verdict, public mode ignores JN_KEY)
  - 2 size sweeps (1200 public and 400 sealed generated inputs, all <= 900 bytes,
    keys in order, k present exactly when pass is true)
- Parity: 305 vectors in vectors/parity.json, generated by scripts/gen-parity.mjs
  from the JS engine run through the same pipeline with the interface overrides.
  The Rust output matches the oracle's verdict string byte-for-byte on all 305.
  parity.json is byte-identical before and after sealed mode, and identical to the
  committed file.
- Sealed: 42 vectors in vectors/sealed.json (10 passes with k, 2 fails, 2

## Sealed jobs (interface section 6.3)

- A `deliverable_ct` field selects sealed mode (src/sealed.rs). main.rs reads
  JN_KEY and passes it in; the library reads no environment, so it stays pure.
- Crypto crates with default features off: chacha20poly1305 (alloc only),
  x25519-dalek (its free `x25519()` clamps per RFC 7748, used for both scalar
  multiplications), hkdf, sha2. getrandom is not in the dependency tree; the import
  list is unchanged (scripts/imports.mjs). base64 is a small strict decoder written for
  this crate (src/b64.rs), with no base64 dependency.
- Independent reference: scripts/sealed.mjs uses Node built-ins only to make K,
  encrypt a deliverable to C, build the provider's secret JSON, seal K to a client
  key, and open k with the client's secret key. scripts/gen-sealed.mjs pairs it with
  the JS engine to write vectors/sealed.json; every vector's outcome must match the
  category in its name, and every k is opened and C decrypted back to the exact
  plaintext in Node, then again in Rust (tests/sealed.rs).
- Decisions the spec leaves open, pinned here (for the interface owner to ratify or
  move into 6.3):
  1. Order, first match wins: invalid_input, too_large, key_missing, bad_delivery,
     then the normal verdict over the plaintext (its own size gate, then the
     criteria), with k on a pass. So key_missing comes before invalid_criteria, as in
     the table.
  2. invalid_input: criteria or deliverable_ct not a string, `deliverable` also
     present, dh or client_pk not exactly 64 lowercase hex.
  3. too_large is checked before the key is read: criteria over 4096 bytes or
     deliverable_ct over 21884 bytes, so an oversized input never touches K. A
     21884-character C without padding decodes to a 16385-byte plaintext; that one is
     too_large from the normal verdict after a good decrypt.
  4. On every sealed error: ch = sha256(criteria) (of "" if criteria is not a
     string), dh = the input dh (sha256("") if it is malformed).
  5. JN_KEY must be exactly 64 hex digits, either case, with no trimming; anything
     else is key_missing.
  6. C must be canonical standard base64 (padding, no whitespace, zero trailing
     bits); anything else is bad_delivery.
  7. A plaintext that decrypts and matches dh but is not UTF-8 is bad_delivery.
  8. A small-order client_pk makes the shared secret all zero. The judge still
     emits k as written (it then opens with the zero secret); rejecting such keys
     belongs in create_job. Node's X25519 refuses that case, so it is pinned by a Rust
     unit test, not a vector.
  9. A stdin carrying both deliverable and deliverable_ct used to be judged as public
     with the extra field ignored; it is now invalid_input, as 6.3 requires.
- The keys in vectors/sealed.json (test_jn_key, test_client_sk) and the fuel
  corpus (*.test-jn-key) are test fixtures derived from fixed public seed strings.
- A verifier without K cannot re-run a sealed verdict; it can check ch, dh, eh and
  the form of k.

## Performance (see RESOURCE-LIMITS.md)

- Whole-word `contains` is linear: each deliverable is indexed once (code points
  + word flags), each term matched with KMP, repeated terms memoized, the
  deliverable parsed/word-counted at most once per evaluation (engine::Ctx).
- Worst case over adversarial-but-valid inputs (16 KB deliverable, 4 KB criteria,
  <=16 checks, sealed included): 602,500,000 instructions (a sealed pass of 16
  nested-anyOf json checks, with k), 1.75 MB linear memory, ~22 ms, measured under
  OutLayer's metering. Sealed adds about 13M instructions to the same checks (16 KB
  decrypt, hash, HKDF, two X25519). The old O(n*m) whole-word scan peaked at 17.4
  billion.
- The escrow requests 50B instructions, 64 MB and 30 s (interface section 4):
  margins about 83x, 36x and 1,300x. scripts/fuel-check.sh guards at 3B.

## Key parity decisions (verified against the JS oracle and empirically)

- serde_json with `arbitrary_precision`: `1e400` parses (as JS JSON.parse does,
  to Infinity); `as_f64()` is None for out-of-range, which is the "non-finite
  number" signal. Numbers compared by f64 value so 1 == 1.0 (JS `===`).
- `length` unit "chars" counts UTF-16 code units (JS `String#length`); json-shape
  minLength/maxLength count Unicode code points (`[...s].length`).
- Word count = maximal non-whitespace runs using the ECMAScript WhiteSpace set
  (includes U+FEFF, excludes U+0085); NOT Rust `char::is_whitespace`.
- `contains` wholeWords uses the code-point reference from the JS test suite.
- schema `typeof`: null and array are "object"; a number is always "number".
- Interface overrides over the JS engine: at most 16 checks (JS allowed 64);
  `http-endpoint` is not a known kind (any such check -> invalid_criteria);
  criteria <= 4096 bytes, deliverable <= 16384 bytes (else too_large).
- err priority: invalid_input -> too_large -> invalid_criteria. err verdicts use
  th:100 and checks:[]. ch/dh are sha256 of the exact decoded strings, or
  sha256("") for a field that could not be read.

## Deviations from a literal JS port (see interface; listed in final report)

- A deliverable nested deeper than serde_json's 127-level limit is "not valid
  JSON" to the Rust `json`/`schema` checkers and fails; V8 would parse it. The
  depth-100 parity vector confirms both agree below the limit; deeper inputs are
  excluded. (Criteria this deep are rejected earlier by the depth-12 gate in
  both, and DEEP_TEXT criteria hit the 4096-byte too_large gate first.)

## Mutation testing

56 planted bugs, 23 of them on the sealed path (k on a fail or with an err, dh not
checked, decrypt failure ignored, UTF-8 not enforced, key_missing and bad_delivery
swapped, wrong HKDF infos, nonce not bound to ch/dh, a salt or AAD added, the wrong

## Fuel regression guard

An adversarial corpus and a guard keep the worst-case instruction count far below
what the escrow requests (the stall vector of interface.md section 4). All measured
under wasmtime fuel, the metering OutLayer uses, on judge.wasm
`911b8a351d199d003735ceef138647ec8485de8eff197aa909f5db496b92c958`.

- `scripts/make-fuel-corpus.mjs` writes 21 inputs to `vectors/fuel/` (committed),
  each within the interface limits. 15 public: ~1,266 empty wholeWords terms over
  spaced and solid 16 KB text (the pre-linearization 17.4-billion case), ~783
  distinct letters and 85 `a..ab` runs each found only at the end (defeating
  memoization), a 1024-unit late mismatch, 16x length / checksum / schema / json
  including nested `anyOf`, ~1,457-item `uniqueBy`, `uniqueBy` over URL domains, a
  max-size emoji+combining deliverable, and a normal scored case. 6 sealed: the two
  heaviest public inputs encrypted (passes with k), a 16 KB plaintext, a max-size
  Unicode plaintext, a full-size bad_delivery and a key_missing. Sealed cases carry
  a `.test-jn-key` sidecar (the test JN_KEY) and an `.expect` sidecar (text the
  verdict must contain, so a case cannot quietly fall back to a cheap error).
- `scripts/fuel-check.sh [cap] [wasm]` runs the judge over every corpus file under
  a fuel cap (default 3,000,000,000, far below the escrow's 50 billion) and fails if
  any case runs out of fuel, prints no verdict, or misses its expected text.

Results on `911b8a35`:
- fuel-check at 3,000,000,000: all 21 cases pass. Negative controls: hiding one
  test key makes that sealed case fail on its missing k; a 50,000,000 cap fails 7
  cases.
- Precise worst case (binary-searched by `scripts/measure-limits.mjs`, which also
  measures the sealed corpus cases): 602,500,000 instructions (sealed pass of 16
  nested-anyOf json checks), 1,792 KiB linear memory (16 json checks over ~1,457
  items), about 22 ms. Sealed alone: 14.9M for a 16 KB pass with a cheap check, 2.6M
  for a full-size bad_delivery, 0.34M for key_missing.
